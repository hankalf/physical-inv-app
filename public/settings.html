      Scanner setup each scanner gets its own link — open it once on the device and add it to the home screen

      On the device: open the link in Chrome (or scan the QR into the address bar), then menu → Add to Home screen. Opening the link signs that scanner in — the server accepts counts from signed-in scanners only. Treat a link like a key: Reset link issues a new one and kills the old, and removing a scanner stops it entirely. A link used more than once is flagged, which is normal after a scanner is wiped and worth a look otherwise.

      What the scanners offer everything a counter is offered on the gun, in one place — the jobs, the comments, the override reasons, the SOS list

      The reasons a site needs are the site's own — "Blocked by a trailer" means something here and nothing anywhere else.       Jobs on the sign-on screen

      The sign-on screen shows exactly the jobs ticked here. Day to day: Cycle count, Front2Back and Not in Location. On the morning of a wall-to-wall, untick those and tick Full count alone, so every scanner opens on it; swap back when it is over. A ticked job with nothing waiting says so when a counter picks it. The practice gun in the Testing Suite has its own ticks, in its sandbox.

      SOS what the SOS button offers

      Every gun has an SOS button. Pressing it offers this list, and whichever one the counter picks lands on the dashboard within seconds — with their team, aisle and last bin — and in a Teams channel if one is set up under Advanced. Write the list in the words your floor uses; the counter is in a hurry.

      Report a problem the kinds of problem, and what must be scanned

      The gun's Report a problem button offers these kinds of problem, each with its reasons; what the counter picks goes on the dashboard's Fix list. Each kind says what the counter must scan to confirm before it is sent, so the office goes to the right place: the bin for racking or a blocked bay, the pallet, the pallet or the bin for a leaning or tipped pallet whose own label may be out of reach, or nothing for a light out. A label that will not scan can be typed, and the fix list says so.

        One-time set-up in Teams (about ten minutes)
        
          
          
        1. In Teams, pick the channel the backups should go to (a private one is best: whoever can open its Files can open the backups). Click ⋯ beside the channel's name → Workflows → Post to a channel when a webhook request is received. Name it Inventory backups, press Next, check the team and channel, and press Add workflow. Close the box that shows an address — it is copied later.
          2. 
          
        2. Open the Workflow to change it: ⋯ in the left bar → Workflows → Inventory backups → Edit.
          3. 
          
        3. Click the first step, When a Teams webhook request is received, and check Who can trigger the flow is Anyone.
          4. 
          
        4. At the very bottom, below every other step, press + (New step) and search for SharePoint → Create file. Fill it in:
            
            
              
          • Site Address — pick the team's site (it has the team's name).
            • 
              
          • Folder Path — the folder button → Shared Documents → the channel's folder (for example General). That folder is what the channel's Files tab shows.
            • 
              
          • File Name — click in the box, choose Expression (fx), type triggerBody()?['backup']?['name'] and press Add.
            • 
              
          • File Content — the same way, the expression base64ToBinary(triggerBody()?['backup']?['contentBase64']).
            • 
            
          5. 
          
        5. Save. Click the first step again and copy the address under HTTP URL (or HTTP POST URL).
          6. 
          
        6. Paste it in the box above, press Save, then Send a test file. Within a minute a card says so in the channel, and a small text file is in its Files tab. If the file is there, the backups will land there too.
          7. 
        
        
        
        Each copy is the backup gzipped, named inventory-….db.gz; unzip it (7-Zip, or double-click on a Mac) to get the database back. A card goes into the channel with each one — take the Post card step out of the Workflow if the channel should stay quiet. A Workflow cannot tidy up after itself, so delete old copies from the folder now and then. The Workflow answers before it saves the file, so this card can only say Microsoft took the copy: the channel's Files tab is where to check it arrived. The address carries its own signature, so treat it like a password: it is kept here and never shown again in full. A copy can be up to 25 MB squeezed, far more than a site's database; the card says so if one is ever bigger. If your company has switched Workflows off, use Google Drive.

        One-time set-up in Google (about ten minutes)
        
          
          
        1. On any computer, sign in to Google with the account whose Drive should hold the backups, and open script.google.com → New project.
          2. 
          
        2. Press Copy the script below. In the editor, select everything that is there, paste over it, and press Save (the disk icon). Name the project Full Harvest backups.
          3. 
          
        3. Deploy → New deployment. Click the gear by Select type and pick Web app. Set Execute as: Me and Who has access: Anyone, then Deploy.
          4. 
          
        4. Google asks to Authorize access: pick the account. It warns Google hasn't verified this app — it is your own script, so press Advanced → Go to Full Harvest backups (unsafe) → Allow.
          5. 
          
        5. Copy the Web app URL (it ends in /exec), paste it in the box above, and press Save and check the connection. The account and the folder show here, and the newest backup goes at once.
          6. 
        
        
        
        
          
        
          
        
          
        
        
        
        
        
        No Google password is stored here. The script runs as that Google account and does one thing: save the backups this server sends into the one folder, keeping the newest few. It only answers a request carrying this server's key, which is written into the script. Anyone who has the web app address and the key could put files in that folder, so treat the address like a password. Disconnect stops sending; Make a new key also stops the old script. A Google Workspace account whose admin blocks "Anyone" web apps cannot do this — use OneDrive, or a personal Google account.

        everyone who changes something is recorded by name in the log

          adjustments and downloads and nothing on teams, warehouse jobs or cycle counts; Admins get everything, Settings

        Systems 
        LIVE, TEST and any other — each at its own address, reached from one sign-in and one scanner link
        
      
        
      
        
        
        
        
        
        
        
          
          
        
        
        
        
          
          
        
        
      
        
      
        
        
        The other systems
        
        
        Each one is the app deployed again at its own address, with its own database. Its address is what people and scanners are sent to when they switch.
        
        
        
        
        
        
        
      
        
      
        
        
        On the scanners
        
        
        Which system the guns count in. With both, the gun's sign-on screen has System to switch. With one alone, every gun goes to it by itself and is offered no other — a gun with counts still to send waits until they have gone.
        
        
        
      
        
      
        
        
        The link key
        
        
        The other systems take people this system sends only when the hand-off is signed with this key. Put it in each of them (Settings → Site & systems → Systems there, or its SYSTEM_LINK_KEY variable).
        
        
        
          
        
          
        
          
        
          
        
        
        
      
        
      
        
      
        
      
        
        
        Who may use each system
        
        
        Admins may use every system. Tick the others a login may switch to; it takes effect the next time they switch. A sign-in handed over lasts twelve hours.
        
        
        
      
        
      
        
        Setting up TEST next to LIVE
        
          
          
        1. In Railway, deploy this app a second time as its own service, with its own volume (its own database), from the branch you want TEST to run.
          2. 
          
        2. Give that service three variables: SYSTEM_NAME = TEST, SYSTEM_HOME_URL = this system's address, and SYSTEM_LINK_KEY = the link key above — no spaces or quotes. Redeploy it.
          3. 
          
        3. Here, Add a system: name TEST (the same name as its SYSTEM_NAME), its Railway address, and under On the scanners choose whether the guns use LIVE and TEST, LIVE only or TEST only. Save, then Check the link: every line should come back ✓.
          4. 
          
        4. Tick who may use TEST in the table. They see Switch to… in the sidebar, and Sign in to on the sign-in box.
          5. 
        
        
        
        Logins live here, on the home system: TEST takes them from the hand-off, with the same role and pages, and nobody has a second password. A scanner keeps its own link: switching hands it to TEST under the same link, and TEST's counts stay in TEST's own storage on the gun. The way back is a button, on the gun and on every TEST page.
        
      
        
    
        

    
        
      
        What is switched on 
        hide the parts nobody here needs yet — for every login, on the office pages and the scanners
        
      
        
        A team with a few days to learn the count does not need cycle counts, front bins or the map in front of it. Untick a part and
        it is gone — from the sidebar, the dashboard tabs, the search box and the scanners' sign-on screen, for everyone, admins
        included — until it is ticked again. Nothing is deleted: the data behind it waits. The count itself is always on: the
        Full Counts page, the dashboard's Progress, Team plan and Second counts, Teams & crew,
        Settings and the guide. A page already open sees the change when it next loads; a scanner the next time it is online.
